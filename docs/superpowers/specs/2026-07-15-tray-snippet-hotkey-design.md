# 托盘代码片段入口与快捷键设置设计

## 目标

- Linux 和 Windows 均保留托盘右键菜单，并将“代码片段”作为首个菜单项。
- 用户可以在设置界面直接按下组合键，配置用于打开“代码片段”界面的全局快捷键。
- 设置界面明确显示快捷键是否绑定成功；绑定失败时不得破坏当前有效快捷键。
- Linux 与 Windows 功能一致，同时沿用各平台现有 UI 技术，避免扩大改造范围。

## 已确认的交互规则

1. 托盘右键仍然打开菜单，不拦截原始右键事件。
2. “代码片段”移动到菜单首项，点击后打开代码片段界面。
3. 快捷键采用直接按键录入：输入控件获得焦点后捕获组合键，并显示规范化文本，例如 `Ctrl+Shift+S`。
4. `F1` 至 `F12` 可以单独绑定；其他按键必须包含 `Ctrl`、`Alt` 或 `Super/Win`，仅使用 `Shift` 不合法。
5. 新快捷键只有在系统注册成功后才保存。注册失败时：
   - 保留原快捷键及其注册状态；
   - 设置窗口保持打开；
   - 在控件附近显示具体失败原因；
   - 不写入失败的配置。
6. Linux 和 Windows 均提供图形化快捷键设置。

## 方案选择

采用“共享快捷键核心 + 平台原生设置界面”。

- 共享层负责快捷键的解析、规范化、规则校验、系统注册、运行时切换和状态查询。
- Linux 在现有 GTK 配置窗口的“通用设置”页增加快捷键控件。
- Windows 使用项目已有的 `eframe/egui` 实现配置窗口，不引入新的 GUI 依赖。

未采用统一 egui 配置窗口，因为这会迫使 Linux 迁移现有同步、通知和关于页面；也不采用独立快捷键窗口，因为它会使设置入口分散。

## 架构

### 配置模型

在 `GeneralConfig` 中增加全局快捷键字符串字段，并通过 serde 默认函数保持旧配置兼容。默认值使用当前行为对应的 `Ctrl+Shift+S` 规范形式。

配置只保存已经成功注册的快捷键。启动时若配置缺失，则使用默认值；若已有配置无法解析或注册失败，应用保持运行并向用户报告，而不是因 `unwrap` 崩溃。

### 快捷键领域模型

新增与 UI 无关的快捷键模块，提供：

- 从按键及修饰键构造候选快捷键；
- 从配置字符串解析快捷键；
- 输出统一的显示/持久化文本；
- 校验 `F1-F12` 单键例外和主修饰键规则；
- 将底层库错误转换为可显示的中文错误。

解析和规则校验使用纯函数，以便在 Linux 主机上完整测试，不依赖真实桌面会话。

### 运行时注册服务

`HotkeyService` 持有 `GlobalHotKeyManager` 和当前有效的 `HotKey`，并负责生命周期管理。应用启动时创建一次服务，事件线程只在收到当前快捷键 ID 的 `Pressed` 事件时发送 `UiCommand::Show`。

切换快捷键采用事务式流程：

1. 解析并校验候选快捷键；
2. 若候选与当前绑定相同，直接返回成功；
3. 先向系统注册候选快捷键；
4. 注册成功后注销旧快捷键；
5. 更新服务中的当前绑定；
6. 保存配置；
7. 向设置界面返回成功状态。

若第 3 步失败，不改变任何状态。若注册新键后注销旧键或保存配置失败，服务需回滚到原绑定，并返回失败，确保内存状态、系统注册和磁盘配置尽量一致。

### UI 与服务通信

快捷键切换必须由共享服务执行，而不是由 GTK 或 egui 控件直接操作底层注册器。设置界面提交完整配置和候选快捷键，应用层先尝试切换快捷键，成功后再保存其余配置并刷新 `SnippetManager`。

为了让窗口在失败时保持打开，保存动作返回结构化结果：成功时允许关闭；失败时携带错误文本并保持当前输入，原绑定状态仍显示为有效。

## 平台界面

### Linux GTK

在“通用设置”页增加“代码片段快捷键”区域：

- 只读录入框或捕获按钮显示当前组合；
- 聚焦后捕获按键按下事件；
- `Esc` 取消本次录入；
- 状态标签用绿色显示“绑定成功”，红色显示失败原因；
- 保存失败后不销毁对话框，用户可重新录入。

现有 `ConfigWindow::show` 的一次性 `run` 流程需要改为响应循环，使校验或绑定失败后能继续显示，而不是直接返回 `None`。

### Windows egui

新增轻量配置窗口，使用现有 `eframe/egui`：

- 读取并展示当前快捷键；
- 点击录入控件后，从 egui 原始按键事件组合修饰键与主键；
- 使用相同共享校验规则；
- 保存时调用相同的事务式绑定流程；
- 在窗口内显示成功或失败状态。

本次 Windows 配置窗口以快捷键配置为必要功能；可展示现有通用配置，但不要求迁移 Linux 的同步提供商配置页面。

## 托盘菜单

- Linux：将现有“代码片段”菜单项移动到菜单首项，继续发送 `UiCommand::Show`。
- Windows：将“代码片段”菜单项移动到菜单首项，执行现有刷新后再发送 `UiCommand::Show`。
- 两个平台仍通过右键菜单操作，不新增原始托盘点击监听。

## 错误处理

- 禁止在快捷键管理器创建、解析、注册和注销路径使用 `unwrap`。
- 启动绑定失败时应用继续运行，托盘菜单仍可打开代码片段界面，并显示桌面通知或设置状态。
- 冲突、格式非法、系统不支持和底层注册失败应转换为用户可理解的信息。
- 设置保存失败不得覆盖磁盘上的最后一个有效快捷键。

## 测试策略

按 TDD 实施，至少覆盖：

1. 旧 YAML 缺少快捷键字段时加载默认快捷键。
2. 配置保存后快捷键可正确往返序列化。
3. `F1-F12` 单键通过校验。
4. 单字母、单数字、仅 Shift 组合被拒绝。
5. 含 Ctrl、Alt 或 Super/Win 的普通按键组合通过校验。
6. 显示文本与持久化文本规范化且可再次解析。
7. 事务式切换成功时更新当前绑定。
8. 新绑定注册失败时原绑定保持不变。
9. 快捷键事件仅在 ID 匹配且状态为 Pressed 时打开界面。
10. 平台菜单构造顺序中“代码片段”为首项（尽可能抽取为可测试数据）。

最终验证包括 `cargo test`、`cargo check`、`cargo build --release`、格式检查和修改文件诊断；可用桌面环境下还应手动验证录入、冲突失败、成功切换以及新快捷键打开代码片段窗口。

## 非目标

- 不替换 Linux 的 AppIndicator 托盘后端。
- 不让右键直接绕过菜单。
- 不全面统一 Linux GTK 与 Windows egui 配置 UI。
- 不增加多个可同时生效的全局快捷键。
